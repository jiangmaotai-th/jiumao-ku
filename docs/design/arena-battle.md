## 2. 回合结构

### 2.1 排序（固定类别序，不看分差）
从“双方都有数据”的榜单里选 8–12 个，按**固定类别顺序**出场，**不按分差、不按互有胜负**编排：

| 顺序 | 类别 | 说明 |
|---|---|---|
| 1 | 人类盲测（Arena 类） | 该类别下双方都有数据的榜单，按 `benchmark_id` 字母序 |
| 2 | 知识 / 推理 | 同上 |
| 3 | 数学 | 同上 |
| 4 | 代码（编程 / 智能体） | 同上 |
| 5 | 综合指数 | 通常是 `aa_index` |
| 最后 | 鹈鹕展示（若有图） | 固定殿后，不造成伤害 |

同一类别内多项时按 `benchmark_id` 字母序，保证同一对模型同一天顺序可复现。排序只决定出场先后，不改变任何一项的伤害。

**无共同数据的类别**：五个计分类别在进度条上各占一格。若某一类别双方没有任何可同台的榜单，仍显示一格**灰掉的进度槽**，标签为「无共同数据」。这一格**不占时长、不计入回合、不产生 `rounds[]` 条目**，只表示“这里空了”。

### 2.2 单回合时间轴（基准 6.5 秒；实际时长见 2.3）
| 段 | 时长 | 画面 |
|---|---|---|
| 招式名横幅 | 1.0 s | 大字必杀技名 + 榜单名 + 来源小字 |
| 蓄力 | 1.5 s | 双方蓄力，能量随分数上涨 |
| 图表揭晓 | 2.0 s | 两边真实分数以图表形式长出（数字滚动到真实值），CI 显示为误差光带 |
| 命中 / 格挡 | 1.0 s | 伤害数字、震屏或火花 |
| 小结 | 1.0 s | “A 92.0% vs B 88.0% · 来源 · **分数日期**”停留，可点开；日期取该条 `source_date` |

### 2.3 整场时长（已定）
记 `scored_rounds` = 本场计分回合数（人类盲测 / 知识推理 / 数学 / 代码 / 综合指数里实际播出的回合；**不含**鹈鹕展示，也不含「无共同数据」灰槽）。

| 段 | 时长 |
|---|---|
| 开场（双方登场 + 赛前预测） | **固定 6 s** |
| 每个计分回合 | `round_s = min(9, max(6.5, 46 / scored_rounds))`，再**向上取整**到 0.1 s（例如 46/6 ≈ 7.666… → 7.7） |
| 鹈鹕殿后（有则加） | **固定 6.5 s**（不计入 `scored_rounds`） |
| 结算（胜负、每回合战报、全部来源列表） | **固定 8 s** |

计算值：`T = 6 + scored_rounds × round_s + (6.5 if 有鹈鹕 else 0) + 8`。

| scored_rounds | round_s（向上取整到 0.1 s） | 无鹈鹕 T | 有鹈鹕 T |
|---|---|---|---|
| 6 | 7.7（46/6→7.7） | 60.2 | 66.7 |
| 7 | 6.6（46/7→6.6） | 60.2 | 66.7 |
| 8 | 6.5 | 66.0 | 72.5 |
| 10 | 6.5 | 79.0 | 85.5 |
| 12 | 6.5 | 92.0 | 98.5 |

说明：`46 / scored_rounds` 的设计是让「开场 6 + 计分合计 46 + 结算 8 = 60」在回合偏少时仍够一分钟；回合 ≥ 8 时每回合回到下限 6.5 s，整场自然长于 60 s。

**验收**：实际播完时长 ≥ 60 s，且不超过计算值 `T + 0.5` s。六个计分回合、无鹈鹕时验收窗为 **60.0–60.5 s**（计算值按上表约 60.2）。**不加假回合**。用户可随时按“跳过演出”直接看结算。某方已被 K.O. 时，剩余计分回合与鹈鹕仍按同一套时长播放（见 3.5）。

单回合内部各段（2.2）在 `round_s > 6.5` 时，把多出的时间按比例加进「图表揭晓」和「小结」。


### 2.4 鹈鹕投票（已定：只展示 + 站内匿名盲投）

鹈鹕固定为**最后一回合**（殿后），时长见 2.3（固定 6.5 s，不计入 `scored_rounds`）。**不计伤害、不改 HP、不影响胜负**。

#### 2.4.1 放置与画面
- **对决页进行中**：两张真实生成图左右并排，标题 **「哪个模型画的鹈鹕骑自行车更好？」**；每图下方一颗 **「这张更好」** 按钮；按钮旁小字 **「匿名盲投，投完揭晓作者」**。另有指向原帖的链接占位（投完才可点开，见下）。
- **左右随机**：同一场对决里，哪边是 A 模型、哪边是 B 模型由服务端按场次随机，前端只显示 **「图A」「图B」**，不显示模型名。
- **匿名**：模型名**不得**出现在图片 URL、`alt`、文件名或任何投前可见的页内数据里。服务端为每场每张图签发**不透明 id**（如 `p_7f3a`）；图片地址与投票的 `pick` 只用该 id，服务端映射回模型。模型名、作者与来源链接**仅在投票之后**由接口返回。
- **无倒计时**：用户可慢慢看再投；未投也可继续看后续（结算页仍提供一次投票入口，见下）。
- **结算页**：若用户在殿后回合未投，结算页再次给出同样的两图 +「这张更好」（仍匿名，左右与进行中一致）。若用户**跳过**投票（离开或点「跳过」），结算页**只揭示来源链接与作者**，**不可再投**该场。
- **首页 15 秒预览**：不出现鹈鹕投票，也不展示票数。

#### 2.4.2 结果展示（先投后看）
- 投完（或该浏览器已投过、本地记住）才显示结果：双方票数、百分比条、总票数，并附注 **「按 IP 计票，仅供参考，不影响胜负」**；同时揭晓两侧对应的**模型名、作者与来源链接**。
- **票数 &lt; 20**：只显示「已投票」与总票数，文案 **「已投票，票数较少暂不公布比例」**，不公布双方占比与具体票数拆分（总票数可显示）。
- 浏览器记住本场已投（`localStorage` 或等价），刷新后直接进入结果态，不再出按钮。
- **局限（需在设计/客服口径里承认）**：任何人若自行检索原图或原帖，仍可能事先知道作者；站内保证的是页内不剧透，不是密码学级盲盒。

#### 2.4.3 事件与接口
- 事件（前端 → `/api/event`，沿用 `arena_pick` 防刷思路）：
  ```json
  {
    "type": "pelican_vote",
    "match": "<YYYY-MM-DD>:<matchup_id>",
    "pick": "<opaque_image_id>",
    "test": true
  }
  ```
  - `match`：擂台日期 + 对决 id，中间冒号；服务端校验日期为**今天或昨天**（UTC+8），且 id 有效；内部存储时品牌/型号对按字母序归一（与 `arena_pick` 一致）。
  - `pick`：服务端下发的不透明图片 id（如 `p_7f3a`），**不是**模型 id，也不是字面 `"a"`/`"b"`。非法 id 直接丢弃。
  - `test?: true`：测试流量照记但不进公开票数（地址带 `?arena-test=1` 时前端自动加）。
- **防刷**：同一 IP 对同一 `match` 只计 **1** 票；另有全局每分钟上限。前端在「已投」态照常显示，避免用户以为坏了；共用出口 IP（公司/学校）后投者可能不计票，结果页已用「按 IP 计票」说明。
- **只读计数接口**：返回该场总票、（票数 ≥ 20 时）两侧票数与占比；投前调用不返回模型名；投后（或跳过揭示时）附带模型名、作者、来源 URL。
- **每日归档**：当天票数随 08:10 备份进档，供事后核对；**不回写**进伤害或胜负。

#### 2.4.4 与回合数据的关系
- `category = showcase`，`result.kind = showcase`，`damage = 0`，`applied = 0`。
- 回合小结与结算来源列表仍列出鹈鹕原帖链接；投票本身不是榜单分。

## 3. 伤害规则

### 3.1 归一化
对每个榜单 b：
- 百分比榜（满分 100）：`D_b = 当日参赛池里该榜 P95 − P5`，下限 10 个百分点。理由：GPQA、AIME 头部都在 90% 以上，用 100 做分母差距全被压扁；用“全场区间”才看得出强弱。
- Elo / 指数榜：`D_b = 当日参赛池 P95 − P5`（取代现在不透明的 `poolSpan`，口径写进数据）。
- 参赛池 = 当日数据里该榜所有模型；`D_b` 写进每回合数据（字段 `norm_span`），前端不自己算。
- 归一差距 `g = |s_A − s_B| / D_b`，截到 [0, 1]。越低越好的榜单（v2 目录里暂时没有）先取反再算。

### 3.2 格挡
- **格挡**：`Δ ≤ 高分方 ci_down + 低分方 ci_up`（沿用现在代码的单侧口径），或没有 CI 时 `g < 0.05`。
- 格挡伤害为 **0**。两个模型非常接近时，整场可以全是 0 伤害，这是真实数据的结果，不做“震伤”或保底伤害。
- 来源不同、口径不同的分数**不能同台**：同一回合两边必须来自同一来源、同一设置（如都取 AA 的 HLE），否则这回合按缺数据跳过。

### 3.3 命中伤害
```
damage = min(22, round(w_cat × (6 + 40 × g)))
```
- 最小命中 ≈ 8，最大 22。
- **暴击**：`Δ > 2 × 格挡阈值` 或 `g ≥ 0.4`，只升级演出，不加伤害（和现在一致）。

### 3.4 类别权重
| 类别 | w | 理由 |
|---|---|---|
| 人类盲测 Arena | 1.0 | 最贴近“用起来好不好” |
| 编程 / 智能体 | 1.2 | 当前最受关注、分差最能体现实力 |
| 数学 | 0.8 | 头部饱和，降低偶然性 |
| 知识 / 推理 | 1.0 | |
| 综合指数 | 1.0 | 已包含其他榜，避免重复计数不加权 |
| 鹈鹕（无投票数据） | 0 | 只演出 |

同一类别最多出 3 回合（Arena 类最多 3 个、编程最多 2 个……），防止某一类刷满整场。

### 3.5 HP、K.O. 后续、胜负、平局
- 双方 HP **100**。单回合封顶 22，所以至少要 **5 次命中胜场**才能把一方打到 0（见下）。
- **`damage` vs `applied`（已定）**：
  - `damage` = 按 3.3 算出的**理论伤害**（格挡为 0；与当前剩余 HP、是否已 K.O. 无关），**只用于**首页预览选回合（见第 5 节）。
  - `applied` = **本回合实际扣掉的 HP**。命中时 `applied = min(damage, 受击方当前剩余 HP)`；格挡 / 展示 / 已 K.O. 后追加回合均为 0。例：对方剩 12 HP、理论 `damage = 22` → `applied = 12`，HP 归零。
  - **画面上的伤害数字显示 `applied`**，与血条掉量一致；战报里可同时保留 `damage` 供核对，但默认展示 `applied`。
- **无残血保护、无护盾吸收**：按 `applied` 如实扣，HP 可在任意回合归零。
- **K.O. 后继续打完**：某方 HP 首次归零时记为 K.O. 时刻，**比赛不提前结束**。剩余回合照样一项项播完，画面进入状态 **「已 K.O.，追加数据」**：
  - 被 K.O. 一方变灰倒地，不再切换攻击/受击姿势，也不再扣血；
  - 两边分数仍对撞显示（真实数据完整呈现）；
  - 顶部持续显示双方回合胜场；
  - 这些追加回合的 **`applied` 一律为 0**（不再扣血）；`damage`（理论伤害，按 3.3）照常计算，供首页预览选回合；`kind` 仍按分差标 `hit`/`crit`/`block`/`showcase`（仅演出与战报，不改 HP）。
- 整场时长规则不变（见 2.3），K.O. 后再短也要把剩余回合播完；验收仍按 2.3（≥ 60 s 且 ≤ T+0.5 s）。
- **回合胜场**：该回合分高且非格挡、非鹈鹕展示即记一胜；**K.O. 后的追加数据回合若分高也计胜场**（只是不再扣血）。
- **胜负以 HP 为准**（已定）：
  1. 有一方被 K.O. → **先被 K.O. 的一方负**（即使其回合胜场更多）。
  2. 无人被 K.O. → **剩余 HP 高者胜**。
  3. HP 相同 → **直接判平局**。**不用**回合胜场加赛。
- **结算主文案**始终同时写结果与回合胜场：
  - K.O.：`Opus K.O. 胜 · 回合胜场 5 : 6`
  - HP 胜：`示例A 胜（HP 52 : 48）· 回合胜场 4 : 5`
  - 平局：`平局 · 回合胜场 X : Y`（例：`3 : 3` 或 `4 : 5`；只以 HP 相同为准，胜场比分原样展示）
- **说明行**（`result_note`）：仅当**胜方的回合胜场少于负方**时出现（K.O. 胜与 HP 胜都一样），例如主文案 `示例A 胜（HP 52 : 48）· 回合胜场 4 : 5`，说明：“血量领先；对方在更多单项上得分。”**平局不出现**说明行。
- 单回合伤害封顶 22 → 打满也至少要 **5 次命中胜场**才能把 100 HP 打到 0。因此 K.O. 胜方在扣血阶段至少已有 5 个回合胜场；若结算时反而少于负方，多出的负方胜场只可能来自 **K.O. 后的追加数据回合**。

### 3.6 碾压与旗鼓相当（只贴标签，不改数字）
- **一边倒 / 碾压**：不做戏剧编排、不做残血保护。若一方回合胜场 ≥ 85%（或提前 K.O. 后追加数据仍明显领先），结算显示“碾压”标签，**不改任何分数或伤害**。视觉上用连续暴击、血条一路掉光、提前进入「已 K.O.，追加数据」来表现。
- **全格挡 / 旗鼓相当**：格挡伤害为 0，整场 0 伤害可以接受。若格挡回合 > 60%，赛前对阵卡可提示“旗鼓相当”，结算按 3.5 判。
- 选手门槛仍见第 4 节（共同榜单 ≥ 6）；**不再**为了“好看”优先挑差距适中的组合——今日擂台按第 9 节热度选人，自选对决由玩家决定。

## 4. 缺数据规则
- 只有**双方都有同一来源数据**的榜单才进入出招池；某一具体榜单缺一方 → 该榜不进 `rounds[]`（结算的来源列表里注明“X 榜：B 无公开成绩，未出招”）。
- **整类无共同数据**：五个计分类别里，若某一类一条可同台榜单都没有，进度条仍留一格灰槽，标「无共同数据」（见 2.1）。不占时长、不计 `scored_rounds`。
- **跑分时效（已定）**：`source_date` 距对决日超过 **6 个月**的成绩视为**无数据**——该榜不出招（等同缺一方数据）；若整类因此没有任何可同台榜单，进度条灰槽「无共同数据」（见 2.1）。**每一计分回合**的小结与角落常驻显示该条分数的日期（`source_date`）。
- **最少 6 个计分回合**才开完整对战（`scored_rounds`，不含鹈鹕、不含灰槽）：
  - ≥ 8：正常对战，每回合 6.5 s（见 2.3）。
  - 6–7：照打，按 2.3 把每回合拉到 `max(6.5, 46/scored_rounds)`（上限 9 s），整场仍 ≥ 60 s。
  - < 6：不开这场。每日对阵自动换下一组（见第 9 节）；用户自选时提示“这两位共同榜单不足 6 个，无法开战”，并给出可比的榜单列表。
- 每日数据脚本：一个模型有效榜单少于 6 个，不进入每日对阵候选。

## 9. 今日擂台自动选人

> 目标：每天自动把“当下用户最关心的一对模型”放上今日擂台（用户举的例子：**Opus 对 ChatGPT**）。本节的打分公式、权重和阈值都是**提案**，数值待易秋和猫汰确认；已定的部分标为“已定”。

### 9.1 时间线（已定）
| 时间 (UTC+8) | 谁 | 做什么 |
|---|---|---|
| 全天 | 前端 → 后端 | 玩家在**自选对决**里自己挑模型、点“开战”时，发一条 `arena_pick` 事件到 `/api/event`（见 9.2）。首页今日擂台、自动播放都**不发**。 |
| 07:30 | 后端（金酱） | 调用可单独测的统计函数，汇总前一天的事件，写 `dist/arena-data/hot-matchups.json`（读的是前一天的 `arena-data`；当天 07:40 才会更新） |
| 07:40 | AI 日报编辑 | 整理新闻时写 `buzz.json`（外部热度）；更新 `arena-data` 里各模型的 `brand` 字段；调用仓库里的选人纯函数（见 9.1.1），写入 `today.json` |
| 08:10 | 后端 | 三份文件随每日备份归档 |

#### 9.1.1 选人逻辑放哪（已定）
- **选人算法**写成一份**纯 Python 函数**，由旺财维护，放在仓库 `scripts/daily/` 下（日期和三份输入文件都从外面传入，方便银酱用假数据单测）。
- AI 日报编辑的每日脚本**只 import 仓库里那份**，07:40 任务只跑仓库版本，不另写一套。
- **统计脚本**（金酱）同样是可单独调用的函数，日期和输入都从外面传。
- **前端**只读 `today.json` 播对决，不跑选人逻辑。

### 9.2 两路信号（已定）
**(a) 站内数据 `hot-matchups.json`**
- **事件格式**（前端发出，后端接收）：
  `{ "type": "arena_pick", "a": "<型号id>", "b": "<型号id>", "test"?: true }`
  - `a` / `b` 是 `arena-data` 里模型的 id（前端选择框用的同一个 key），不是品牌名。
  - A 对 B 与 B 对 A 算同一对（服务端按字母序归一）。
  - 不记任何个人信息。
- **品牌字段**：`arena-data` 里每个模型有一个 `brand` 字段，由 AI 日报编辑维护。后端统计时用这份字段把型号归到品牌；前端显示也读同一份，出了新模型只在一个地方补。
- **未知品牌**：07:30 统计时读的是前一天的 `arena-data`。刚上架、还没有 `brand` 的型号，当天计入 `unknown`，并在 `hot-matchups.json` 里列出；第二天 `brand` 补上后自动归到对应品牌，不丢数据。
- 防刷：同一 IP 同一对一天只算 1 次；每对每天最多计入约 **200** 次（全局兜底，防轮换 IP）；另有全站每分钟总上限。
- 测试：带 `test: true` 的事件照常记录但**不进排名**（页面地址带 `?arena-test=1` 时前端自动加）。这个标记只能排除自己，不能用来加分。

**(b) 外部热度 `buzz.json`**
- AI 日报编辑记录最近被讨论最多的模型（按品牌），每条都带来源链接和日期；新发布的版本单独标出。没有来源的条目不算。

### 9.3 选人算法（**提案**）
记号：品牌对 `p = {X, Y}`；前一天站内计数 `c_p`（已去重、封顶、去掉测试）；`N = Σ c_p`（全站当日有效事件总数）。

1. **读入**：`hot-matchups.json`（前一天）、`buzz.json`（当天）、最近 7 天的 `today.json` 历史。任一文件缺失，按 9.7 处理。
2. **站内份额**：`S_site(p) = c_p / N`；`N = 0` 时全为 0。
3. **外部份额**：每个品牌的热度分 `b_X`（= 当天带来源的讨论条数，按来源去重，发布新闻 ×2，提案），归一化成 `s_X = b_X / Σ b`；一对的外部份额 `S_buzz(p) = √(s_X · s_Y)`（几何平均：两边都得有热度，才不会被一个大热品牌拖着随便配对）。再把所有 `p` 归一化，使 `Σ S_buzz = 1`。
4. **随数据量爬升的权重**：
   `w_site = min(0.5, N / 1000)`，`w_buzz = 1 − w_site`
   站点刚起步（N 很小）时几乎全看外部热度；有效事件到 1000 条后，站内和外部各占一半，不再继续加。
5. **总分**：`H(p) = w_site · S_site(p) + w_buzz · S_buzz(p)`，从高到低排成候选队列。
6. **新人插队**（规则 3）：某品牌在 `buzz.json` 里标了 `new_release`，且发布在 7 天内、当天 `s_X ≥ 2 × 前 7 天平均`（提案阈值），则它和“与它配对 H 最高的对手”组成的对直接排到队首，`today.json` 保留 `新人` 标记。同一天多个新人，按 `s_X` 高者优先。
7. **7 天不重复**（规则 1）：最近 7 天（含昨天、不含今天）上过擂台的品牌对，从队列中跳过，下一对顶上。新人插队也受此约束。
8. **品牌 → 具体版本**（规则 2）：热度按品牌算，出战按版本算。对每个品牌按下面顺序选一个型号（型号 id 与 `arena-data` 一致；版本名照抄跑分来源写法，不用我们自己起名）：
   1. **玩家最常选**：看 `hot-matchups.json` 里该品牌下的 `models` 明细，取被选次数最多的那个型号；若它与对手当前候选型号在同一来源下至少有 **6** 个共同榜单，就用它出战。
   2. **否则用当天跑分最高**：在双方共同榜单上按第 3.1 节归一化后取平均；无法比较时取 LMArena 文本榜上排名最高的版本（提案）。档位（high/max 等）按第 8 节问题 5 的结论处理。
9. **共同榜单检查**（规则 4）：两个版本在**同一来源**下至少有 **6** 个共同榜单（第 4 节），不足就试下一对。
10. **输出**：队列里第一个通过 7–9 步的对，写入 `today.json`（9.6），并记下被跳过的对和原因。选人函数签名（概念）：`select_featured(date, hot_matchups, buzz, history) -> featured`，三份输入和日期都从外面传入。

例（**示例数据，不是真实统计**）：N = 240 → `w_site = 0.24`。若 `S_site(Claude, OpenAI) = 0.40`、`S_buzz = 0.30`，则 `H = 0.24×0.40 + 0.76×0.30 = 0.324`。

### 9.7 边界情况
- **同分**：H 相同依次比：S_buzz 高者 → 站内 `count` 高者 → 距上次上擂台更久者（从没上过算最久）→ 品牌对字母序。保证结果可复现。
- **没有一对合格**（全被 7 天规则或 6 榜规则挡掉、或两份输入都空）：退回**原来的选法**（v1 现有逻辑），`reason.kind = "fallback"`，并写明原因。原逻辑选出的对如果共同榜单也不足 6，再放宽 7 天不重复规则（只放宽这一条），仍不行就沿用昨天的擂台并标注。
- **`hot-matchups.json` 缺失或过期**（日期不是昨天）：当作 N = 0，只用外部热度，在 `inputs` 里注明。
- **`buzz.json` 缺失**：只用站内数据（`w_site` 视为 1）；两份都缺 → 兜底。
- **品牌映射到版本失败**：该品牌下玩家最常选的型号共同榜单不足 6、且当天跑分最高的版本也找不到 / 来源对不上 / 多个版本分数完全相同无法区分 → 该对记 `version_unmapped` 跳过，试下一对；同时在日报的待办里列出，由 AI 日报编辑补 `brand` 或映射。不猜版本名。
- **同品牌对战**（如 Opus 对 Sonnet）：自选对决允许，事件照常记；统计进 `same_brand_pairs`，**不进** `pairs`，因此不进今日擂台候选（已定）。
- **`brand` 缺失**：07:30 时还没有 `brand` 的型号计入 `unknown`，列入 `unknown_models`；不因缺字段丢弃事件。第二天字段补上后自动归到对应品牌。
- **新人数据不够**：新模型刚发布，共同榜单常常不足 6 个，照规则 4 不能上擂台，只能排到下一对；新人标记等数据够了再用。
- **封顶**：某对碰到 200 封顶（`capped: true`）时照常计 200，同时提醒金酱看是否刷榜。

## 10. 回合记录（已定）
### 10.1 目的
战斗回合节奏快（每回合 6.5–9 s，见 2.3），分数对撞一闪而过，玩家不知道这一回合比的是什么。**每回合结束后，在画面边上留一条记录**，整场打完可以从头翻到尾。

### 10.2 每条记录写什么
| # | 内容 | 写法 / 示例（**示例数据，不是真实成绩**） | 取自 |
|---|---|---|---|
| 1 | 回合号 | 「第 3 回合」 | `BattleResult.rounds[]` 的下标 + 1（见 10.5） |
| 2 | 测试项目名和类别 | 「SWE-bench · 代码」 | 回合的 `benchmark_id` 显示名 + `category`（见 10.5） |
| 3 | 双方真实分数，带单位 | 「72.0% vs 58.0%」「1310 vs 1288 Elo」；越低越好的榜在分数后标「越低越好」 | `a.score` / `b.score`、`unit`、`higher_is_better`（见 10.5） |
| 4 | 胜方，用**文字**写明 | 「左方胜」「右方胜」；不只靠阵营色 | `winner`（`'a'` / `'b'` / `null`） |
| 5 | 本回合实际伤害 | 「-22 暴击」；被 K.O. 那一回合等于对方剩余血量 | `applied`（**不用** `damage`）；暴击看 `crit` |
| 6 | 特殊情况（只在出现时写） | 见下 | 见下 |

第 6 项的几种情况：
- **一方缺数据**：按第 4 节，缺一方的榜不进 `rounds[]`，所以不会有“半条”回合；对应的是**整类无共同数据**的灰槽，记录里写一行「代码 · 无共同数据（原因）」，不编回合号。原因字段规则输出里没有，见 10.5。
- **格挡（平局）**：`winner === null && blocked === true`，写「格挡 · 分差在误差内，0 伤害」。
- **鹈鹕回合**：`showcase === true`，写「鹈鹕展示 · 不计分」；投票比例按 2.4.2 **先投后看**——投之前不写比例和作者，投完写比例，<20 票只写「已投票，票数较少暂不公布比例」。
- **终结技 K.O.**：打出 K.O. 的那一回合写「K.O.！」；之后的回合（`afterKo === true`）写「已 K.O.，追加数据」，伤害写 0。

### 10.3 保留多少条
- **一场比赛的每个回合都保留，不设上限**；开新的一场就清空。
- 手机版（**战斗画面**宽度 < 600px，不看屏幕宽度）：默认显示最近 3 条，点开看全部。
- 结算页：整场记录全部展开，和比分汇总放在一起。
- 首页 15 秒预览不显示回合记录（预览只放一个回合，见第 5 节）。

### 10.4 数据来源与布局
- **只读规则函数 `resolveBattle()` 返回的 `rounds[]`**（以及同一份回合数据 JSON 的展示字段），不另外存一份记录数据。记录内容与战斗演出必须来自同一个对象，保证永远一致。
- 布局、动效与无障碍以小瞳 `visual-scheme.md` **2.5** 为准（归美术）：电脑在战斗画面右侧窄栏，宽为战斗画面的 22%（最小 180px、最大 300px），按容器算不按视口；**最新一条在最上面**；开了「减少动态效果」时不闪，改静态高亮；记录区 `role="log"` + `aria-live="polite"`。

### 10.5 规则输出里没有、需要开发补的字段
核对 `src/arena/rules.ts`：`BattleRound`（继承 `RoundResult`）现有字段为 `winner`、`blocked`、`crit`、`gap`、`damage`、`showcase`、`applied`、`hpA`、`hpB`、`afterKo`；`BattleResult` 另有 `ko`（只给败方，不给回合号）。以下记录内容**规则输出里没有**，请旺财定从哪里带（回合 JSON 透传或扩展类型），不要在记录组件里自己再算一份：
1. **回合号**：`BattleRound` 无 `round` 字段，目前只能用数组下标；第 6.1 节 JSON 有 `round`，需确认两者一致。
2. **测试项目名 / 类别**：`RoundInput` 有 `category`，但 `BattleRound` 不带；`benchmark_id` 及其显示名都不在规则输出里。
3. **双方真实分数、单位、越低越好**：`RoundInput.a/b.score`、`higherIsBetter` 不回传到 `BattleRound`；`unit` 在规则里完全没有（只在 6.1 JSON）。
4. **缺数据原因**：规则里没有；灰槽来自 6.3 的 `category_slots`（`status: no_shared`），也没有原因字段。
5. **鹈鹕投票比例**：规则里没有，来自 `pelican_vote` 接口（2.4.3）。
6. **K.O. 发生在哪一回合**：`BattleResult.ko` 只有败方；可由“`applied > 0` 且某方 HP 变 0”推出，或补 6.3 的 `at_round`。

### 10.6 验收用例（给银酱）
1. 每条记录的胜方、`applied`、暴击/格挡与 `resolveBattle()` 对应回合逐项一致；回合号与出场顺序一致。
2. 分数显示与回合数据的 `a.score` / `b.score` 和单位一致；越低越好的榜带「越低越好」。
3. 格挡回合显示「格挡」与 0 伤害文字；鹈鹕回合显示「不计分」，投票前不出比例，投后按 2.4.2 显示（含 <20 票文案）；K.O. 回合显示「K.O.！」且伤害等于对方剩余血量；之后回合显示「已 K.O.，追加数据」、伤害 0；无共同数据的类别显示灰槽文字及原因。
4. 整场 N 回合全部保留（用 ≥ 10 回合的数据测，不被截断）；开新一场后记录清空。
5. 战斗画面 < 600px 时默认只显示最近 3 条，点开显示全部；结算页全部展开。
6. 每条不看颜色也能读出胜方和数值。
7. 鹈鹕投票接口未上线或请求失败时，鹈鹕回合记录显示「暂无投票数据」，页面不报错。
8. 某个榜缺 `unit`、`higherIsBetter`、`category` 或类型不对时，该榜不出招、不生成回合（与第 4 节缺数据处理一致），回合号连续不断号；跳过原因不显示在页面上：每日数据脚本生成时就应拦下并写进脚本日志；前端读数据时再兜底跳过，原因只在开发环境控制台打印。若因此整类没有可同台榜单，按灰槽「无共同数据」显示。
9. 开启「减少动态效果」时最新一条不闪，改为静态高亮；读屏软件能自动播报新增的一条。
10. 战斗画面正好 600px 和手机竖屏时，记录栏不遮挡角色和血条；首页 15 秒预览不显示记录栏。
